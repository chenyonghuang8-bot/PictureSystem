## 2. Native authentication: explicit transport, same security model

Add dedicated JSON credential endpoints `/api/v1/auth/android/login`, `/reauth`, `/password`, `/logout`; shared authenticated reads/mutations may accept either transport via one strict helper. Android login returns `{token,expiresAt,serverNow}` with ANDROID session, no Set-Cookie. Web endpoints keep their existing response/Cookie contract. Reauth rotates the existing session's token without extending absolute expiry; password replacement preserves the caller's client type and existing revoke-all semantics. No JWT/refresh-token system or relaxed password/Argon2 parameters.

`readSessionCredential(request)` returns `{token,expectedClientType:'WEB'|'ANDROID'}` from exactly one valid transport. Bearer is a single canonical `Bearer <43-character canonical base64url token>` (reuse token validator), no duplicate Authorization/raw header folding/comma, no query token, no alternate header. Reject **any Cookie header plus Authorization**, not only a recognized session cookie. A malformed Authorization must never fall back to Cookie. Credential and mutation-policy selection occur centrally before dispatch.

| Request | Accepted policy |
| --- | --- |
| WEB Cookie, authenticated GET/HEAD | Existing cookie syntax, WEB session, current session/actor authorization. |
| WEB mutation, including TUS writes | Existing exact HTTPS Origin allowlist, JSON guard where JSON; existing TUS content/version/offset guards. |
| ANDROID Bearer, authenticated GET/HEAD | ANDROID session only; no Cookie; if Origin is present reject it (native requests omit it). |
| ANDROID Bearer JSON mutation | Same ANDROID/session checks; strict application/json and schemas/body limits; no Origin/Cookie. No X-Mobile bypass. |
| ANDROID TUS create/PATCH/HEAD | Same bearer checks; existing TUS protocol/content/size limits. No JSON requirement on offset+octet-stream PATCH. |
| Android login and native invitation preview/consume | Separate explicit route; no Cookie, Authorization or Origin; strict JSON, shared rate/capacity limits and service validation. These routes are not authenticated origin exemptions for other operations. |
| WEB token in Bearer, ANDROID token in Cookie, mixed/duplicate credentials | Reject; no transport guessing from a client-supplied body clientType. |

The absence of Origin is not proof of a trusted app; security comes from the bearer/credential/invitation secret plus server authorization. Web CORS remains exact and is not broadened. Production native transport is HTTPS; do not infer trust from a forged forwarded header.

Thread expectedClientType from trusted route/helper → AuthService.authenticate/login issuance → auth repository → `AuthContext` → `Phase1CActor` and every actor adapter. Require exact DB session type in lock-time predicates and final mutations. Audit all `readWebSessionCookie`, `requireTrustedJsonOrigin`, service.authenticate callers and literal WEB SQL predicates in auth, albums/search/memories, uploads/TUS, derived serving/viewer/downloads, Phase1C, shares and Trash. Existing operations remain permission-gated even when not exposed in the Android UI. Anonymous public-share routes do not become bearer-authorized private routes.

Preserve 256-bit opaque token, SHA-256-only DB storage, 30-day absolute login expiry, 7-day idle limit, current 15-minute recent-auth and throttled last_seen update, user/member disable/left checks, password proof and all existing lock ordering. Retain same expiry on reauth and transport-checked revokeByToken/logout. Logout-all/revoke session/password invalidate both transport types as appropriate; list sessions reports actual type. No raw token/hash/Authorization in logs/errors/analytics. COMMIT unknown/rollback failure still uses existing connection discard and no transaction replay.

Native credential controller stores only the small session record in **expo-secure-store**, never AsyncStorage/SQLite/URL. On launch/resume load it then call `/auth/me` before showing private lists/resuming uploads; local expiry is advisory, server is authority. Single-flight rotation blocks dispatch with the old token, durably replaces SecureStore before exposing the new session, increments request epoch, and invalidates pending media/cache/queue calls. Lost rotation/password response requires fresh login, not retries that guess the new token. SecureStore write failure leaves the app unauthenticated; never continue with an unpersisted credential. Logout immediately clears UI/token and pauses queues even offline; online perform unregister/revoke first when possible, but cleanup failure must not retain local authentication.

Pass them through the trusted TUS context into upload repository, not unvalidated arbitrary upload metadata. A same-operation retry must match immutable declared size/filename/MIME and original sorted target set; otherwise 409 conflict. Under existing family/actor locks, find the same operation **before quota reservation/insertion**, so it never double-reserves. Distinguish reused versus newly created receipt to the service. Reused create must not call createUploadPayload, truncate staging or mark an old live upload FAILED because exclusive-create sees EEXIST. Return its original Location/status; do not generate a replacement ID behind an existing operation.

The current protocol's random namingFunction generates the server upload ID, not an idempotency key: exclude that random ID, session/token and timestamps from the fingerprint. A duplicate operation returns the repository's existing upload.publicId through `toTusUpload`/Location, even if the TUS library proposed a new random ID for this request. Never use that unused proposed ID for staging, result lookup or failure mutation. Test the actual HTTP Location, not just repository dedup. ### Safe result and placement

Add owner-only `GET /api/v1/uploads/:uploadId/result`, `PUT /api/v1/uploads/:uploadId/targets` and `POST /api/v1/uploads/:uploadId/placement` (JSON). Authenticate and enforce receipt.created_by_member_id belongs to current actor and same family, even for admin. Do not use guessed mediaId as the input. GET/result is observational, never creates placement.

Public result contains receipt status/offset plus bounded processing category `PENDING|READY|FAILED|UNAVAILABLE` and placement category `PENDING|NEEDS_ALBUM_ACTION|APPLIED`; retain retryability, not internal worker epochs, hashes, paths, producer states, canonical source/uploader, dedup flag or other albums. Before an authorized placement/visibility proof, **omit mediaId and albumId entirely**, even if hidden dedup canonical media is already READY. READY category describes availability of this uploaded content, not permission to browse an older owner's record. No terminal processing failure is inferred from absence of a job. Map repository failure codes to fixed safe categories, not raw parser errors.

GET/result performs its own checked locking transaction: family X → current actor user/session/member locks → owner receipt → storage → canonical media → current derived assets → target rows, then current target album/grant/placement reads under the same family X serialization. Use deterministic row order within each set and retain current actor/token-type checks. No nested repository transaction or cached prior authorization. Re-read server time after all potentially blocking reads and assert the actor immediately before producing the DTO. The source may disappear or become retired/inactive; return only the owner's safe receipt/category result, without a stale media identity. To include any mediaId/albumId, require an actual **current** live target placement, current visible-album ACL for this actor, active canonical media and valid current-generation/recipe READY assets in that same observation. Historical APPLIED alone never suffices. Choose the minimum currently visible target album ID; do not enumerate invisible ones. Family X is the existing same-family serialization boundary; no OS/CapacityGate wait is entered while this transaction holds SQL locks.

Placement is explicitly resumed by the authenticated foreground queue, not an unauthenticated background privilege. It waits for COMPLETE, the existing reconciler's canonical identity and actual current-generation/recipe valid preview+thumbnail READY/IMAGE eligibility. It must not call canonical creation or manufacture READY. Use a dedicated repository transaction for this receipt-based operation, sharing existing permission helpers rather than invoking `addAlbumMedia` as a nested transaction.

Acquire K **L-S** from nonlocking owner-receipt/storage discovery before SQL; then checked transaction: family X → current actor user/session/member locks → selected albums ascending → relevant grants ascending → receipt X → storage S → canonical media X → current derived rows in deterministic kind/ID order → target rows ascending → album_media rows. Revalidate receipt ownership/K/COMPLETE, source binding, AVAILABLE storage, active lifecycle, current generation/recipe/readiness, and **every** selected live album's canView plus existing canUploadToAlbum OR canEditAlbum policy, with fresh server time after waits. No SQL lock before L acquisition; no R/CapacityGate is needed for this DB-only placement. Family X serializes current same-family business mutations; preserve established auth/native order.

One transaction inserts all pending selected placements idempotently and marks the same target rows APPLIED with locked DB time. **This commit is placement's linearization point**. Any target denial/deletion rolls back the whole pending set; no partial silent success. A valid owned COMPLETE receipt is proof of uploading the same bytes, so authorized placement can use the existing canonical even when its earlier source is private; it must preserve that source and expose no prior metadata/album membership. This implements the existing architecture's same-family dedup/add-target rule without a media-ID discovery endpoint.

Retries observe APPLIED and do not recreate manually removed placement; an APPLIED target is never reopened by this queue. PUT/targets may atomically replace only the all-PENDING set after explicit user selection and current ACL checks; freeze it once any APPLIED exists. A lost placement COMMIT response triggers fresh result/current target observation, not blind insert replay. If a placement was removed or access revoked afterward, APPLIED may remain historical but result must suppress media/album IDs and report NEEDS_ALBUM_ACTION/unavailable, without restoring it. Return a viewer link only after a fresh current visible placement/ACL/readiness check, selecting a currently visible target album. Trash/purge/retired receipt cannot be resurrected. No target-list schema change or background auto-placement is left for later design.

## 5. Native persistent queue

Use `expo-sqlite` for bounded **non-secret** job metadata and `expo-file-system` app-private document storage for owned immutable source copies. SecureStore is for session/install secrets and pending invitation token only. Source files are not secrets-vault values and must not be put in SecureStore; queue SQLite contains no bearer/password/FCM raw token. Exclude private copies, SQLite queue and transient media from Android cloud backup/device transfer; no auto-export.

Use the system document/photo selection flow with read permission only for explicitly selected images. Chosen path: copy selected bytes into an app-private queue directory, then size/hash verify and atomically rename from `.partial`; only then commit a queue row. Do not depend on a picker cache URI surviving restart, and do not rotate/transcode/rewrite EXIF. DocumentPicker's immediate cache copy is a staging input, not durable queue storage. Reject unreadable/changed/source-missing files with an actionable reselect state; never silently attach a different file to an old upload ID.

Concrete limits: 50 unfinished jobs, 2 GiB aggregate private queued source bytes, 256 MiB per selected image (also obey stricter server/device free-space limits); one active upload, at most two binary preview loads concurrently. Check space with a reserve and enforce quotas before copying; bounded streaming hash/copy, not 2 GiB RAM. This is foreground photo upload, not generic 32 GiB video client support. Explain selection-limit failures without changing the server's existing 32 GiB policy.

Queue keys include API environment, userId and familyId; each job stores local random job/operation ID, private relative path, immutable size/hash, safe display name/MIME, selected album IDs, server uploadId if known, stage, server-confirmed offset, retry/backoff metadata. Durable states: COPYING (recover/remove only own partials), WAITING, UPLOADING, FINALIZING, PROCESSING, PLACING, DONE; orthogonal PAUSED_AUTH/PAUSED_USER/RETRY_WAIT/NEEDS_ACTION/CANCELLED. Never persist “COMPLETED” from local bytes alone. SQLite transactions persist operation before create, upload ID before PATCH, confirmed offsets/stage after responses. Crash between network response and local commit resolves through the operation/HEAD/result endpoints.

App background pauses selection of new requests and settles/cancels the current bounded request; foreground reauthenticates and re-HEADs. OS death does not guarantee a cancellation response or progress, but restart reconstructs state. 401 pauses all that account's jobs; 403/404 album/receipt denial requires action; transient network/408/429/5xx/storage unavailable uses capped jittered backoff (1,2,4…60 s, then manual retry after 8 consecutive failures), respects Retry-After and connectivity/AppState. No infinite tight polling: processing/result poll at ≥2 s then cap at 30 s while foreground; terminal server FAILED is not ordinary network failure.

Logout/account/family switch increments epoch, aborts old requests, clears UI, and pauses old jobs without sending old account data under the new bearer. Old queued data is inaccessible in the new account's screens. Offer explicit deletion or resume only after reauthentication to the owning account; never silently migrate a queue. Source copies may be deleted after confirmed placement DONE, explicit cancel/delete, or confirmed terminal upload abandonment; do not delete at byte completion. On startup clean only self-owned `.partial` and orphan files after correlating the queue, not arbitrary directories. DONE retains only a bounded receipt summary (latest 100), no source bytes. Cancel calls existing owner abort when legal, then deletes only local copies; it cannot undo a committed Original or purge media.

## 7. Real FCM registration, installed-device ownership and account changes

Use **expo-notifications.getDevicePushTokenAsync** native FCM token, not Expo Push Token / Expo sending service. Create an Android notification channel then request notification permission in context (My → device notifications); denial leaves album functionality usable and status NOT_ENABLED, not REGISTERED. Subscribe to token-change events and register the supplied token once; do not call token acquisition inside its own token listener. No sending credentials, campaigns, background handler, media payloads or notification deep-link navigation in this scope.

Provider preconditions: user creates/selects a Firebase project and Android app matching final package; supply its local google-services configuration without secrets in commits/logs. No server service-account key is required merely to store registrations. Real token generation still contacts Firebase; disclose device registration, not photo transfer. Confirm device/emulator Google Play services compatibility. Missing Firebase/GMS yields a clear BLOCKED/UNAVAILABLE registration state, never a dummy token success. Huawei/Honor branding alone answers neither APK nor FCM capability.

New `android_device_registrations`: surrogate BIGINT PK; `installation_id BINARY(16)` unique; `installation_secret_hash BINARY(32)`; `user_id` nullable FK; `session_id` nullable FK; `provider` fixed FCM; raw token VARBINARY(4096) nullable; `token_hash BINARY(32)` nullable unique; `revision BIGINT UNSIGNED NOT NULL` initially 1; created_at/updated_at/last_seen_at/unbound_at; CHECK token/raw hash null together, and binding user/session/null pairs consistent. Store raw token only in restricted application DB because later delivery needs it, never in public DTO/log. SHA-256 index plus byte equality detects collisions; a hash collision is fail-closed, not overwrite. Do not expose lists of other devices/tokens. No media/family FK: session/account is the ownership scope.

On first installation the client will create independent random installation ID and 256-bit installation secret in SecureStore (not generated by this design task). Authenticated ANDROID PUT `/api/v1/android/devices/:installationId` carries installation proof, expected revision (zero only for absent row), native FCM token and bounded device label. Server stores proof hash, never raw secret. Bearer proves user session, **not ownership of a claimed token/device**. Existing installation changes require matching install proof and exact revision CAS; duplicate FCM token owned by a different installation is rejected generically, never stolen/reassigned because a bearer supplied it. Reinstall/lost proof requires new installation and fresh FCM token; do not recover by guessing old installation/token.

The install secret is a narrowly scoped registration-management capability, not a new login credential, session model, device attestation or proof Firebase issued that token to this hardware. On first claim the server can validate format/bounds and uniqueness but cannot independently prove possession of a previously unseen FCM address. Record registration as an authenticated client claim; real-native acquisition is separately required acceptance evidence. Do not introduce attestation, challenge pushes or a sending service to disguise that limitation. The proof only prevents changing an **existing** installation record without its capability, and the token unique index prevents overwriting another recorded installation. It grants no family/media access. Keep this limitation explicit for any future sending-system design.

Register/rotate/unbind response contains only installationId, revision, bound flag, updatedAt. Authenticated owner+installation-proof DELETE unbinds and clears token/hash; retain proof/revision tombstone to fence late requests. A proof-authenticated, current ANDROID session may bind this same installation to its new account using exact revision, atomically clearing the old binding/token. Old-account delayed writes with previous revision fail. Client serializes one device operation at a time and rejects epoch-stale responses; 409 re-reads safe current status using proof before an explicit current-session retry. Never disclose old owner IDs.

DB order for device operations: nonlocking locate only; lock all involved old/new user rows ascending → relevant sessions ascending → installation row → conflicting token row(s) deterministic ID order; read DB time after locks and validate current ANDROID session/proof/revision. If nonlocking lookup's owner/revision changes, rollback/re-discover rather than acquiring a new user lock out of order. No family/media locks and no reverse device→user lock acquisition. Use checked transactions, bounded deadlocks and no unknown-COMMIT replay; outcome resolution via fresh proof-scoped read.

Extend logout/revoke/logout-all/password-change transactions after their existing user/session locks to unbind registrations tied to invalidated sessions, locking registry IDs ascending. Rotation within the same session preserves registration; password replacement requires registration with the new session. User disable also makes registrations ineligible immediately via bound session/user validity; there is no sender to drain. Define eligibility now as live bound user + matching live ANDROID session + absolute/idle limits, not merely nonnull token. Offline logout cannot guarantee a remote unbind request arrived: delete local auth immediately, expose no registered-success assumption, and next authenticated installation rebind uses proof/revision. No notification can be sent in this Phase because no sender is introduced.

## 10. Official external evidence checked for this design

These are external platform facts, separate from repository evidence, not proof this workspace built successfully:

- [Expo SecureStore](https://docs.expo.dev/versions/latest/sdk/securestore/): Android Keystore-backed encrypted storage, restart persistence, uninstall loss and backup exclusion; implementation must handle storage failure.
- [Expo Notifications](https://docs.expo.dev/versions/latest/sdk/notifications/): getDevicePushTokenAsync supplies native FCM token; create Android channel before permission/token flow; token listener must not recursively fetch a token.
- [Firebase Android FCM setup](https://firebase.google.com/docs/cloud-messaging/android/get-started): supported Google Play device or Google APIs emulator requirement and Firebase Android configuration. This is why Huawei/Honor model/OS/GMS and the absent Firebase project are real gates, not assumptions.
- [Expo DocumentPicker](https://docs.expo.dev/versions/latest/sdk/document-picker/) and [FileSystem](https://docs.expo.dev/versions/latest/sdk/filesystem/): picker cache-copy/read behavior and app file APIs inform the explicit durable private-copy design; cache URI alone is not the persistence contract.
- [Expo local native build](https://docs.expo.dev/guides/local-app-development/): local native compilation is distinct from web export and release variant alone does not establish formal signing.
- [Android network security configuration](https://developer.android.com/privacy-and-security/security-config) and [app signing](https://developer.android.com/studio/publish/app-signing): debug-only certificate configuration and APK signing/verification. No global trust bypass or generated signing credential was performed in this review.
