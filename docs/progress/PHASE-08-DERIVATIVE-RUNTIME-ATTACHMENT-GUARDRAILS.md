## Exact existing locking and fencing to preserve

The process owns Original writer and Derived writer for its lifetime. This is distinct from per-content OS locks and SQL transactions.

- Claim/recovery: nonlocking bounded discovery, then family SHARE → media UPDATE → job UPDATE; read DB time after locks. `job-repository.ts:180`–265, 366–429. Claim increments attempts and epoch with CAS and sets the existing 90-second lease (`:19`, `:231`). Filter IMAGE_DERIVATIVES explicitly; never claim arbitrary job types.
- Rendering: `OriginalReader.withVerifiedOriginal` (`packages/storage/src/index.ts:639`) takes **R-S only**, verifies the immutable Original, and passes a single-use registered handle to `renderUnverifiedCandidate` (`:863`). Release this render occupancy before acquiring L. Do not wrap rendering in L-S, SQL or CapacityGate, or hold R and then try to acquire L. Existing registered handoff/settlement and fixed supervisor remain mandatory.
- Derivative mutation: processor `:324` takes **L-S → R-S**, re-describes the source/fence, then performs the bounded write phase; releases R then L. Final inspection takes CapacityGate only while L/R remain held. No SQL locks are retained while acquiring L, R or CapacityGate.
- Admission: **L-S → R-S → CapacityGate → MySQL capacity GET_LOCK on the same checked physical connection → family UPDATE → media UPDATE → job UPDATE → derived row/accounting**. See `derived-admission.ts:38`, `capacity-transaction.ts:38`–115 and `derived-admission-repository.ts:275`–335. Admission does not take the storage row lock; do not inaccurately add it to this existing order.
- Asset/READY transitions: **family SHARE → storage SHARE → media UPDATE → job UPDATE → derived rows**, DB time after locks, as `derived-asset-fence.ts:105`–180. These transactions do not retain SQL locks while entering a new capacity lock. Lease includes worker identity, epoch, expiry, job RUNNING/type, media/job generation, recipe, AVAILABLE storage, active lifecycle and lifecycle revision (`:88`–100, `:142`–167).
- Preserve the existing initial heartbeat (`image-derivative-processor.ts:100`) and repository expiry checks; do not invent an unfenced timer or extend lease duration. A long run may become stale. L/R are cross-process native coordination, not replacements for DB epochs. CapacityGate already serializes same-process users and takes the OS lock (`storage/src/index.ts:1900`–1968); sharing it with uploads is supported. Do not nest its non-reentrant methods.

## Startup, shutdown, recovery and unknown outcomes

Open DerivedStore only after the API's successful existing storage assessment and gate/reader setup. Assert the existing INIT1 namespace; never initialize/adopt/repair a root or provision lock files here. `DerivedStore.open` checks the writable root identity (`derived-store.ts:673`). The renderer uses the existing fixed binaries and per-run build/sandbox checks; `runSyntheticRendererStartupProbe` is explicitly synthetic-only (`storage/src/index.ts:807`) and must not be presented as real renderer qualification. No arbitrary executable/fallback or implicit native build is allowed.

Start the loop only after successful API startup, and keep its promise observed. Process one job at a time; stop flag prevents the next recovery/claim, idle wait is interruptible. On SIGINT/SIGTERM/startup failure/onClose: stop new claims, drain the current processor operation and renderer/handoff settlement, drain API requests, then close DerivedStore, reader, CapacityGate, root, and finally DB pool. Resource cleanup must also cover listen failure. Never close borrowed resources underneath a running promise, swallow close failure, or drop process ownership before handoff settles. Existing API onClose currently omits closing CapacityGate (`index.ts:210`); the attachment must own and close it after drain.

For recovery, bounded nonlocking selection of expired RUNNING IMAGE_DERIVATIVES followed by existing `recoverExpiredLease` suffices for lease recovery. Preserve backoff, max attempts and epoch CAS. Do not reset attempts, force availability, manually assign READY or create replacement jobs. Existing old-epoch PUBLISHING + matching final can be inspected and adopted through processor/READY transaction; RESERVED uses existing adoption/admission. Missing final, sealed temp only, mismatched/incomplete inventory or ambiguous residue is retained/fails closed under existing behavior. No new filesystem cleanup/republication/reconciliation algorithm is approved; recovery is not a promise every historical interrupted job automatically becomes READY.

Any thrown DB failure, rollback failure, or unresolved COMMIT_UNKNOWN stops the derivative driver until an explicit restart; no catch-and-continue or `jobs.fail/retry` compensation. Existing final READY unknown may perform its one `readSucceeded` resolution (`image-derivative-processor.ts:307`); verified success is accepted without replay, otherwise stop. Preserve `transaction.ts:78`–100: COMMIT-phase failure destroys the connection, rollback failure discards it, only known pre-COMMIT deadlock retries. A fatal loop error must be surfaced with a fixed safe category and settle shutdown; do not log raw errors, receipt fields, media paths or GPS. Restart uses fresh identity and current DB/filesystem facts, never replays the uncertain transaction.

## Remaining precise upstream design blocker

Actual new uploads need a durable, restart-safe use of the existing canonical-media and enqueue primitives. The minimal candidate is a bounded COMPLETE-receipt catch-up attachment, not another scheduler or a new finalize transaction. However its source selection/cursor, duplicate receipts, canonical source, trash/purge races, lifecycle occupancy and crash-between-create-and-enqueue behavior must be settled explicitly. A post-response fire-and-forget call alone loses work on crash. A query selecting only receipts without media misses crash-after-media/before-job. Replaying upload finalize or forcibly reviving trashed/purging canonical media is forbidden.

Existing `createOrGetCanonicalMedia` locks family → upload receipt → storage (`media-repository.ts:113`–120); it must not simply be enclosed in an unrelated transaction or asserted to share the derivative lock sequence. This review does not change that protocol. Resolve this bounded ingress attachment before granting approval for the full upload-to-map patch; do not expand into full media scheduling, video processing, old Phase 7 issues or production deployment.
