## 2. Calendar policy, one server anchor

Fixed policy `memories-v1`, zone `Asia/Shanghai`, kinds `ON_THIS_DAY` and `LAST_YEAR_WEEK`. No request `date`, timezone, date range or arbitrary anchor browsing parameter.

Implement a small pure calendar helper (`packages/contracts/src/memories-calendar.ts`, exported through contracts) accepting an injected server instant and returning `anchorDate` (YYYY-MM-DD), `zone`, `policy`, `serverNow` (UTC ISO), `nextMidnight` (UTC ISO), and each kind's date predicate bounds. Use Gregorian numeric date parts, a leap-year helper and UTC-only surrogate arithmetic for date-only add/subtract/weekday operations; never host-local getters or parsing a wall date into the photo's real instant. Use explicit Asia/Shanghai Intl date parts for the server anchor; compute the following local midnight with the applicable zone offset and verify its formatted date/time, not the browser timezone. The contemporary application zone is UTC+08; do not apply any Shanghai conversion to media timestamps.

Repository obtains `readServerTime(connection)` **once after family/actor locks** for each request and passes that same instant to assertActor and the helper. Both home cards run from this one context, in the same checked transaction. No second independent today calculation for another card or pagination query. The injected test clock must be an internal dependency/seam, never an HTTP override or production environment date switch.

Effective photo date is `DATE(m.captured_local_at)` when present, otherwise `DATE(m.uploaded_at)` from the canonical media record. Expose exactly that literal date as `timelineDate` and derive `dateBasis=CAPTURE_LOCAL|UPLOAD_UTC` from the same branch. Fallback is visibly labeled 上传日期. Ignore captured_at_utc/captured offset for matching; OFFSET_UNKNOWN remains usable wall time. Later dedup receipts never replace uploaded_at/source. Existing timeline_key remains the stable sorting/cursor key, not a request to re-interpret the photo in Shanghai.

- ON_THIS_DAY: effective year strictly less than anchor year, same numeric month/day. February 29 matches only actual February 29 in earlier leap years; no February 28/March 1 substitution.
- LAST_YEAR_WEEK: subtract one **calendar year** from the anchor, clamping February 29 to February 28 only for this subtraction. Find Monday of the week containing that resulting date; use `[Monday, following Monday)` over effective dates. Do not subtract 365 days or match ISO week number. Do not add a calendar-year filter that would incorrectly exclude the December portion of a cross-year week.

Required fixed examples:

| Anchor | Prior-year date / last-year week |
| --- | --- |
| 2026-10-05 | 2025-10-05 → [2025-09-29, 2025-10-06) |
| 2026-01-01 | 2025-01-01 → [2024-12-30, 2025-01-06) |
| 2024-02-29 | **2023-02-28** → [2023-02-27, 2023-03-06); reject the supplied webpage's 2025 typo |
| 2025-02-28 | 2024-02-28 → [2024-02-26, 2024-03-04) |

Shanghai midnight is 16:00Z of the prior UTC date. An UPLOAD_UTC fallback `2025-10-04T23:30:00Z` still has timelineDate `2025-10-04`, even though the server's Shanghai day is October 5.

## 4. API, cursor, errors and no-store

Add GET `/api/v1/families/:familyId/memories/preview` (both cards) and GET `/api/v1/families/:familyId/memories?kind=...&limit=...&cursor=...` through existing album route authentication/handling. Strict contracts reject extra keys, malformed date/cursor, arrays and invalid bounds. Return approved gallery item identity/dimensions/flags/URLs only, plus timelineDate/dateBasis. No EXIF/GPS/path/storage hash, private filename, hidden album ID or raw database row. Preview has kind-specific items and hasMore; it need not mint a continuation cursor at its different fixed page size. Full page starts afresh when opened.

Context contains kind (per card/page), anchorDate, zone, policy, serverNow, nextMidnight. First-page clients cannot set anchorDate. Cursor is canonical strict base64url JSON using a dedicated version/schema and the existing scope mechanism. Bind scope to authenticated userId, familyId, kind, anchorDate, zone, policy and effective page limit; payload includes last timelineKey/mediaId and those date-context fields. Recompute scope from authenticated/request context, never trust an actor/family field inside a token. Keep max 1024 encoded/768 decoded bytes, strict keys, canonical UTF-8/base64url and exact timestamp validation, positive uint64 ID strings. Hash scope is context binding, not a secret/MAC; editing a last key can at most reposition within the fully authorized **current** result set, not grant permissions or select arbitrary dates.

The repository validates cursor anchor against its newly computed Shanghai today on **every** page, after current actor authorization and before media query. Zone/policy/kind/limit/scope/version mismatch is existing 400 INVALID_REQUEST. A well-formed/context-bound anchor which is no longer today gets **409 MEMORIES_ANCHOR_EXPIRED**, using the existing `{error:{code,message}}` error envelope, with a fixed message and no private data. Add this narrowly typed code to the existing error contract/translation used by these routes; do not return a generic 500 or reinterpret all INVALID_REQUEST errors as rollover. No future/past anchor is honored even if an attacker recomputes an unsigned scope. Auth failure takes precedence over a rollover response.

API success, empty and error responses, proxy responses and SSR fetches must all be `Cache-Control: private, no-store`; no ETag/shared cache/cached loader. Add a narrow Next proxy using existing forwarding behavior, preserving mixed credentials for the API to reject. Do not let proxy/SSR log request query/cursor or cookie/authorization. Routes/pages remain dynamic. Derived serving retains its own existing fresh authorization and physical verification; list membership is not a serving capability.

## 5. Client clock/auth lifecycle and existing Viewer

Create a Memories controller/component around existing PhotoGrid/Viewer rather than forking the viewer. `/memories` selects only the two fixed kinds through URL state. Home preview cards share one server preview response/context; never fetch each card with its own independent clock. Keep cards compact, labeled with the exact period and fallback date basis. Empty state is normal and has no hidden-media hints. A Memories failure must not blank the rest of the home gallery.

Maintain an increasing request **epoch** keyed by userId/familyId/kind/anchor, plus AbortControllers and an alive flag. Every response including 200 must match the captured epoch and current actor/family/kind before applying. Append only matching-anchor pages, dedup media IDs, and use server-supplied visible albumId for Viewer. Do not infer album access from a cached card or persist private items/cursors in localStorage/shared caches.

On logout, actor/family/kind change, unmount, anchor expiry or authentication failure: abort outstanding requests, increment epoch, clear items/cursor and close Viewer. Clear old data before issuing replacements. A late successful response from an aborted old epoch must be ignored. Viewer download/details routes remain unchanged and reauthorize; 401/auth loss closes and clears, 403/404 cannot retain stale private details.

Use serverNow/nextMidnight with an explicit conservative deadline: capture monotonic `requestStarted` before each client fetch; on receipt compute `deadline = requestStarted + (nextMidnight - serverNow)`. Because the server samples after the request starts, this expires no later than the actual server midnight, even when the SQL transaction or network finishes late. If receipt time is already at/past this deadline, reject that 200 before displaying/appending it; otherwise schedule invalidation at the deadline. Do not start a fresh full-day budget at response arrival. Reject invalid/nonpositive context durations. Timer expiry invalidates state immediately and bootstraps the first page. SSR lacks this client request-start bound, so keep Memories content provisional/hidden until a client first-page/preview revalidation supplies it; the ordinary home gallery remains available. `visibilitychange` when visible, pageshow (including BFCache), and history back/forward must invalidate/revalidate current auth/date via a fresh first-page/preview request before exposing retained private content; no stale-card flash from a restored snapshot. A timer alone is insufficient because suspended tabs can miss it.

For one activation/revalidation cycle, allow **at most one automatic first-page bootstrap in a single shared budget across 409 MEMORIES_ANCHOR_EXPIRED, expired late-200 rejection and timer expiry**. Clear state first and consume the budget before dispatch; concurrent triggers cannot each start a bootstrap. The bootstrap and its response/timer remain in the same cycle, even if a conservative early deadline causes the server to return the old anchor again. Any second expiry/rejected 200, or failed bootstrap, clears stale content and shows retry UI without another automatic bootstrap. Internal response handling, epoch changes and timers never reset this budget. Only a new explicit user retry or genuinely later external lifecycle activation starts a new cycle. API responses sampled just before midnight can arrive afterward: reject them using the conservative deadline above, then bootstrap only if that shared budget remains. Initial SSR context is provisional until client revalidation where its freshness cannot be established; nextMidnight never allows arbitrary client-selected dates.
